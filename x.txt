5. I3C Transfer Types

The important thing here is to first understand how communication actually takes place on an I3C bus. Later, when we discuss ENTDAA, CCC, IBI, etc., you’ll already understand the transfer framework.

⸻

📘 Wiki Content — I3C Transfer Types

5.1 Overview

I3C supports multiple types of bus transfers to accommodate different communication requirements.

At a high level, I3C communication can be categorized into:

* SDR (Single Data Rate)
* HDR (High Data Rate)
* I²C legacy transfers

I3C also defines different transaction types based on the direction and intended recipients of the communication:

* Private transfers
* Common Command Code (CCC) transfers
* Broadcast transfers
* Directed transfers
* In-Band Interrupt (IBI) transfers
* Hot-Join requests

The controller determines which type of transfer is performed and controls the bus accordingly.

⸻

5.2 SDR — Single Data Rate

SDR (Single Data Rate) is the fundamental I3C transfer mode.

SDR provides the primary mechanism for normal I3C communication and is designed to provide significantly higher performance than traditional I²C while maintaining a relatively simple signaling scheme.

A simplified SDR transaction can be represented as:
START
  ↓
Dynamic Address
  ↓
R/W
  ↓
ACK
  ↓
Data
  ↓
ACK
  ↓
Data
  ↓
ACK
  ↓
STOP

SDR uses:

* SCL for clocking
* SDA for bidirectional data
* Open-drain signaling for specific bus phases
* Push-pull signaling for normal data transfer

⸻

5.3 SDR Addressing

During a normal private SDR transfer, the controller first identifies the target using its 7-bit dynamic address.

The address is followed by the R/W bit, indicating whether the controller is requesting a read or performing a write.

Conceptually:

┌──────────────┬─────┐
│ 7-bit Address│ R/W │
└──────────────┴─────┘

The target responds according to the protocol-defined acknowledgment mechanism.

Once the target has been selected, data can be transferred between the controller and target.

⸻

5.4 Private Transfers

A Private Transfer is a transfer between the controller and a specific target.

Private Write

Controller
    |
    | Address + Write
    ↓
 Target
    |
    | Data
    ↓
 Target

The controller sends data to a specific target.

Private Read

Controller
    |
    | Address + Read
    ↓
 Target
    |
    | Data
    ↓
Controller

The target provides data requested by the controller.

Private transfers are typically used for normal device-specific communication.

⸻

5.5 CCC Transfers

Common Command Codes (CCC) are standardized I3C commands used for common bus and device management operations.

CCC transfers are broadly classified into:

Broadcast CCC

A Broadcast CCC is intended for all applicable targets on the bus.

                 Controller
                     |
                    CCC
                     |
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
    Target A      Target B      Target C

Directed CCC

A Directed CCC targets a specific device.

                 Controller
                     |
                CCC + Address
                     |
                     ↓
                  Target B

CCC transfers are used for operations such as:

* Dynamic address assignment
* Device identification
* Bus management
* Enabling/disabling target capabilities
* Reading device characteristics

⸻

5.6 SDR vs HDR

I3C defines HDR (High Data Rate) modes in addition to SDR.

The purpose of HDR is to provide significantly higher data throughput than normal SDR communication.

The I3C specification defines multiple HDR modes, including:

* HDR-DDR
* HDR-TSP
* HDR-TSL

Each HDR mode uses a different signaling/encoding approach and has different use cases.

For a basic I3C implementation:

I3C
 |
 ├── SDR
 |
 └── HDR
      ├── HDR-DDR
      ├── HDR-TSP
      └── HDR-TSL

SDR is generally the fundamental mode that must be understood before studying HDR.

⸻

5.7 HDR-DDR

HDR-DDR (High Data Rate — Double Data Rate) transfers data on both clock edges.

Conceptually:

SCL:  ┌───┐   ┌───┐   ┌───┐
      │   │   │   │   │   │
──────┘   └───┘   └───┘   └───

SDA:    D0      D1      D2
        ↑       ↑       ↑

Data can be transferred on both the rising and falling edges of the clock, increasing throughput compared with single-edge transfer.

HDR-DDR is intended for high-speed data transfer between I3C devices.

⸻

5.8 HDR-TSP and HDR-TSL

I3C also defines:

* HDR-TSP — Ternary Symbol Pure
* HDR-TSL — Ternary Symbol Legacy

These modes use ternary-symbol-based signaling to achieve high data rates.

They are more complex than SDR and are generally less important for an introductory I3C session.

For most firmware engineers starting with I3C, the recommended learning order is:

SDR
 ↓
CCC
 ↓
Dynamic Address Assignment
 ↓
IBI
 ↓
HDR

5.9 I²C Legacy Transfers

One of the important characteristics of I3C is its ability to coexist with compatible legacy I²C devices.

The I3C controller can perform transactions that allow supported I²C targets to communicate on the shared bus.

Conceptually:

                    I3C Controller
                          |
                    I3C Bus
              ┌───────────┼───────────┐
              ↓           ↓           ↓
          I3C Target   I3C Target   I²C Target

The controller must use bus operations that are compatible with the legacy I²C target.

This enables gradual migration from I²C to I3C.

⸻

5.10 Broadcast vs Directed Communication

This distinction is important when discussing CCC.

Broadcast

The controller sends a command that applies to multiple targets.

Controller
     |
     | Broadcast
     |
 ┌───┼────┬────┐
 ↓   ↓    ↓    ↓
 T1  T2   T3   T4

Directed

The controller selects one particular target.

Controller
     |
     | Directed
     |
     └──────────> Target 2

This distinction is primarily important for CCC operations.

⸻

5.11 Transaction Terminology

Some useful terms when analyzing I3C transfers are:

START

Indicates the beginning of a transaction.

STOP

Indicates the end of a transaction.

Repeated START

Allows the controller to start another transaction without releasing the bus between operations.

ACK / NACK

Used to indicate whether a transfer element has been accepted or whether the receiving side is not acknowledging it.

Dynamic Address

The address used by an I3C target for normal communication after address assignment.

⸻

5.12 Simplified I3C Communication Flow

A typical system can be visualized as:

                 Bus Initialization
                        |
                        ↓
               Dynamic Address
                  Assignment
                        |
                        ↓
                Normal Operation
                        |
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
      Private       CCC Commands     IBI
       Transfer
          |
       ┌──┴──┐
       ↓     ↓
     Write   Read

HDR modes can be entered when higher data throughput is required.

🧠 Understanding — I3C Transfer Types

The easiest way to understand I3C transfers is to imagine that the controller is the person coordinating a conversation.

There are basically two questions:

Question 1: Who am I talking to?

That’s determined by the address.

Question 2: What kind of conversation am I having?

That’s determined by the type of transfer.

⸻

1. SDR is your starting point

Don’t think of SDR as just another optional feature.

Think:

SDR is the basic communication mode you should understand first.

Imagine:

Controller → Target

The controller says:

“I want to talk to device 0x20.”

Then:

“I want to write.”

or:

“I want to read.”

Then the actual data is transferred.

So:

Address → Direction → Data

is the basic mental model.

⸻

2. Private transfer = “I want to talk to this one device”

Suppose you have:

Target A = Temperature sensor
Target B = Accelerometer
Target C = PMIC

If the controller wants temperature:

Controller
     |
     | Address of Target A
     ↓
Target A
     |
     | Temperature data
     ↓
Controller

That’s a private transfer.

It is basically normal device-to-device communication.

⸻

3. Write vs Read

This is exactly the same basic concept you may already know from I²C.

Write

Controller ───────> Target
                  Data

Example:

“Configure sensor sampling rate to 100 Hz.”

Read

Controller <─────── Target
                  Data

Example:

“Give me the current temperature.”

⸻

4. CCC is different from a normal private transfer

This distinction is important.

A normal private transfer generally means:

“I’m talking to a particular device’s application/register interface.”

CCC means:

“I’m performing a standardized I3C bus/device-management operation.”

For example:

Controller
    |
    | GETPID
    ↓
Target

or

Controller
    |
    | SETNEWDA
    ↓
Target

These aren’t arbitrary sensor commands. They are defined by the I3C specification.

⸻

5. Broadcast vs Directed CCC

Imagine the controller wants to send a command to everyone:

“All devices, disable this feature.”

That’s Broadcast CCC.

             Controller
                 |
              Broadcast
          ┌──────┼──────┐
          ↓      ↓      ↓
         T1     T2     T3

But if it says:

“Target 2, change your address.”

that’s Directed CCC.

Controller ───────────> Target 2

This distinction becomes extremely important when we study Dynamic Address Assignment.

⸻

6. Why HDR exists

Imagine SDR gives you:
Data → Data → Data → Data

but your application needs significantly more throughput.

You could increase the clock frequency, but there are electrical and protocol limitations.

HDR provides additional mechanisms for transferring more information per unit time.

Think of it as:

SDR:
One lane

HDR:
More information per clock / more efficient signaling

Don’t memorize the exact HDR modes yet.

For now:

SDR = fundamental I3C communication

HDR = higher-throughput communication modes

We’ll revisit HDR later after you understand SDR properly.

⸻

7. One important correction about ACK

Since you’re coming from an I²C background, be careful here.

You may be tempted to think:

“I3C is exactly the same as I²C: address → ACK → data → ACK.”

That’s not a safe mental model.

I3C has different acknowledgment and signaling behavior depending on the transfer phase and mode.

For example, HDR modes do not simply follow the traditional I²C ACK-per-byte model.

So for now, remember:

I3C retains some familiar transaction concepts from I²C, but its detailed signaling and acknowledgment rules are different.

When we do the actual SDR waveform, we’ll go bit-by-bit.

⸻

8. The most important flow to remember

For now, keep this in your head:

                    I3C Communication
                           |
             ┌─────────────┴─────────────┐
             │                           │
            SDR                         HDR
             │                           │
      Normal communication       Higher data rate
             │
       ┌─────┴─────┐
       ↓           ↓
    Private       CCC
    Transfer    Transfer
       │           │
    ┌──┴──┐    ┌───┴────┐
    ↓     ↓    ↓        ↓
  Write Read Broadcast Directed

And separately:

Target → Controller
       IBI

IBI isn’t simply a normal controller-initiated private transfer; it is a target-initiated bus request mechanism.

🔬 Spec-Level Points You Should Know

Since you specifically asked me to include specification knowledge, these are the details I’d keep in your preparation notes even if you don’t put all of them on the Wiki:

* I3C defines SDR and multiple HDR modes.
* HDR modes include HDR-DDR, HDR-TSP, and HDR-TSL.
* SDR uses a 7-bit address for I3C device addressing.
* I3C supports Dynamic Address Assignment in addition to static-address mechanisms.
* CCCs are divided into Broadcast CCCs and Directed CCCs.
* Private transfers are controller-to-specific-target transactions.
* I3C supports coexistence with compatible legacy I²C devices.
* IBI and Hot-Join are target-initiated bus requests and should not be mentally treated as ordinary controller-initiated private transfers.
* HDR is not simply “SDR at a faster clock.” The HDR modes introduce different signaling/encoding mechanisms.
* The exact electrical behavior of SDA/SCL changes depending on the phase/mode, so avoid drawing one generic “I3C waveform” and presenting it as applicable to every transaction.
