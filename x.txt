4.1 I3C Fundamental Principles

I3C supports multiple communication formats over a common two-wire interface.

The two wires are:

* SDA — Serial Data: Bidirectional data signal.
* SCL — Serial Clock: Normally used as the clock signal. In certain HDR modes, SCL can also function as a bidirectional data signal.

An I3C Bus can carry multiple types of messages:

1. SDR Messages
    * I²C-like Single Data Rate communication.
    * In I3C Basic v1.1.1, SDR supports SCL clock speeds up to 12.5 MHz.
2. Broadcast and Directed Common Command Code (CCC) Messages
    * CCC provides standardized bus-management and device-management commands.
    * A Broadcast CCC can communicate with multiple applicable Targets.
    * A Directed CCC targets a specific Target.
3. HDR Messages
    * High Data Rate modes provide higher data rates per equivalent clock cycle.
    * I3C Basic v1.1.1 includes HDR-DDR and HDR-BT.
    * HDR-TSP and HDR-TSL are not included in I3C Basic v1.1.1.
4. Legacy I²C Messages
    * An I3C Bus can include supported Legacy I²C Target Devices.
    * The I3C Controller can communicate with these devices using I²C-compatible messaging.
5. Target-Initiated Requests
    * An I3C Target can initiate a request toward the Controller.
    * Examples include an In-Band Interrupt (IBI) and requests associated with Target/Controller functionality.

Frame-Based Communication

I3C uses a Frame encapsulation approach.

A Frame contains a Data Payload, and the transfer protocol for that payload can be SDR or HDR.

At a high level, an I3C Frame contains:

START → Header → Data → STOP

The Header following START is important because it provides the mechanism used for bus arbitration and Target addressing.

Target Devices can also participate in Header Arbitration for mechanisms such as:

* In-Band Interrupt (IBI)
* Hot-Join
* Secondary Controller functionality

HDR communication is entered through appropriate Common Command Codes. Once in HDR mode, the communication format is different from the Legacy I²C message format and follows the signaling rules defined for the particular HDR mode.

Controller Ownership

An I3C Bus permits only one Controller to have control of the bus at a time.

I3C provides mechanisms that allow the Controller role to be transferred from one capable Device to another.

Therefore, although multiple I3C Devices may have Controller capability, simultaneous Controller operation on the same bus is not permitted.

Key Principle

The I3C Bus can therefore be viewed as a common two-wire bus supporting multiple communication mechanisms:

                         I3C BUS
                       SDA + SCL
                           |
        +------------------+------------------+
        |                  |                  |
       SDR                HDR           Legacy I²C
        |                  |                  |
   Private/CCC       HDR-DDR/HDR-BT     I²C Targets
        |
   Target Requests
      IBI / etc.

This architecture allows I3C to combine high-performance I3C communication, standardized bus management, and Legacy I²C interoperability on the same physical bus.

Understanding

The most important thing to understand from 4.1 is that MIPI is defining I3C as one bus with multiple communication formats, rather than one single type of transaction.

The physical interface is still just SDA + SCL, but what those two wires carry depends on the current protocol mode.

Think of it like this:

SDA and SCL are the road. The different message formats are different types of traffic using that road.

The first important type is SDR. This is the fundamental I3C communication mode and is deliberately based on I²C-like signaling. This is why someone familiar with I²C will recognize things such as START, STOP, addressing and clocking when they first look at I3C.

The second category is CCC. CCC isn’t simply another type of application data. It provides standardized commands that allow the Controller to manage and communicate with devices at the bus-management level. For example, later in the specification you’ll encounter CCCs involved in address assignment and device configuration.

The third category is HDR. This is where we should be careful not to think:

“SDR, but with a faster clock.”

That’s not the right mental model. HDR has different signaling/protocol rules and is designed to achieve more data per equivalent clock cycle. The I3C Basic v1.1.1 specification includes HDR-DDR and HDR-BT, while HDR-TSP and HDR-TSL are explicitly outside I3C Basic. 

Then there are Legacy I²C messages. This is a major architectural principle of I3C: an I3C bus can contain supported I²C Target devices. The I3C Controller therefore needs to be able to communicate with both I3C Targets and Legacy I²C Targets.

Now comes one of the biggest conceptual differences from traditional I²C: the Target isn’t necessarily completely passive.

A Target can initiate certain requests toward the Controller. For example, an IBI allows a Target to effectively say:

“Controller, I need your attention.”

Hot-Join provides another Target-initiated mechanism for a device that wants to join an already-running bus.

The specification then introduces the concept of an I3C Frame. This is important because it gives us a common structure for understanding the protocol:

START
  ↓
Header
  ↓
Data
  ↓
STOP

The Header is especially important. It isn’t merely “the address.” The specification says the Header following START allows Bus Arbitration, and it can be used for addressing Targets as well as Target-initiated mechanisms such as IBI and Hot-Join. 

Finally, there is Controller ownership.

You can have multiple I3C Devices that are capable of being Controllers, but you don’t have multiple Controllers simultaneously controlling the bus. At any particular point, one Controller has control of the bus. I3C defines mechanisms for transferring that Controller role.

So if you remember only one diagram from 4.1, remember:

                    I3C BUS
                  SDA + SCL
                       |
        +--------------+--------------+
        |              |              |
       SDR            HDR          I²C
        |              |              |
   Normal I3C      High-speed      Legacy
   communication   communication  devices
        |
       CCC
   Bus/device management

        ↑
        |
 Target can also initiate
 certain requests
        |
    IBI / Hot-Join

This is the architectural picture that the rest of the specification builds upon.

One important spec detail: the specification states that I3C is initialized/configured in SDR mode, not HDR mode. HDR is entered from SDR using the defined mechanism. That is why SDR is the right place to start when we move into Section 5 — I3C Protocol.

4.2 I3C Controller and Target Devices

4.2 I3C Controller and Target Devices

An I3C Bus always has:

* One Controller
* One or more Targets

An I3C Device may be designed to function as:

1. An I3C Controller only
2. An I3C Target only
3. Both an I3C Controller and I3C Target

However, a Device with both Controller and Target capabilities cannot operate as both roles simultaneously. It must be configured to operate as either a Controller or a Target at a given time.

Controller

The I3C Controller is responsible for controlling the I3C Bus and initiating bus transactions.

A Controller-capable Device may be initialized as the Controller of the bus or may initially operate as a Target.

When multiple Controller-capable Devices exist, only one Device may initially be configured as the Controller.

Target

An I3C Target listens to the I3C Bus for commands from the Active Controller and responds to commands applicable to it.

A Target may respond to:

* Broadcast Common Command Codes
* Directed Common Command Codes
* Private transfers addressed to the Target
* Other applicable protocol operations supported by the Target

A Target may also have additional capabilities, such as requesting attention from the Controller through mechanisms defined by I3C.

Controller-Capable Devices

A Device may combine Controller and Target capabilities.

For example:

        +---------------------------+
        |      I3C Device           |
        |                           |
        |  Controller capability   |
        |            +              |
        |  Target capability       |
        +---------------------------+

Such a Device does not simultaneously operate as both roles. Its active role determines how it participates in the bus.

Active Controller

The Active Controller is the Controller currently responsible for controlling the I3C Bus.

The specification distinguishes the Active Controller concept from the permanent capabilities of an I3C Device.

For a bus with multiple Controller-capable Devices, the Controller role can be transferred between capable Devices using the mechanisms defined by the specification.

Therefore:

I3C Device capability
        |
        +---- Controller capable
        |
        +---- Target capable
        |
        +---- Both
                 ↓
       Current active role
        Controller OR Target

Only one Device is the Active Controller at a given time.

Understanding

This section is easy to misunderstand if we think of Controller and Target as permanent hardware categories.

The specification makes a more subtle distinction.

An I3C Device can be designed as:

Controller only
Target only
Controller + Target capable


If a device has both capabilities, that does not mean it can simultaneously behave as both.

Imagine a device that has both capabilities:
             I3C Device
                 |
        +--------+--------+
        |                 |
 Controller capability  Target capability
At a particular point in time, it has an active role:

        Controller
           OR
         Target

This becomes important for systems containing multiple Controller-capable devices.

For example:

             Device A
        Controller-capable
                 |
                 |
          +------+------+
          |   I3C BUS   |
          +------+------+
                 |
             Device B
        Controller-capable

Both devices have the capability to act as a Controller, but the bus still has only one Active Controller at a time.

Initially, Device A might be the Controller:

Device A → Active Controller
Device B → Target

Later, through the mechanisms defined by the specification, the Controller role can be transferred:

Device A → Target
Device B → Active Controller

This distinction between capability and current role is very important when we later study multiple Controllers and Controller handoff.

Now consider a normal Target.

A Target listens to bus traffic and determines whether a command is relevant to it. For example, if the Controller sends a Directed CCC to Target X, Target X processes it while other Targets don’t.

But Targets aren’t necessarily completely passive. I3C provides mechanisms through which a Target can initiate specific types of requests toward the Controller.

This is why I3C’s architecture is more sophisticated than the traditional mental model of:


Master → Slave
The modern terminology is:

Controller ↔ Target

where the Controller normally initiates transactions, but the protocol provides defined mechanisms for Target-initiated requests.

The specification also makes an important physical/system-level point: there isn’t a fixed specification-level limit of “11 I3C Targets.” Earlier versions contained such a number based on typical electrical assumptions, but the actual number depends on factors such as trace length, capacitive loading and the mixture/types of devices on the bus. 

So the clean mental model for Section 4.2 is:

                    I3C BUS
                       |
              +--------+--------+
              |                 |
         Active Controller    Targets
              |
       controls bus
              |
       +------+------+
       |             |
   initiates      manages
   transfers       bus

And in a more advanced system:

      Controller-capable Device
                  |
             Current role
              /       \
       Controller     Target
              |
        Controller role
        can be handed
        to another
        capable Device

That distinction—what a device is capable of vs. what role it currently has—is one of the most important things to carry forward into the later protocol sections.

Now let’s move to Section 4 of the MIPI I3C Basic specification: Technical Overview.

This section is informative, so it is mainly giving us the architectural picture before we get into the detailed protocol definitions in Section 5.

The first important point is that I3C is not just one type of message.

I3C uses a common two-wire interface consisting of SDA and SCL, but multiple communication formats can use those two wires.

The first and most fundamental one is SDR, or Single Data Rate.

SDR is the I²C-like communication mode and is the default mode of the I3C bus.

Then we have CCC, or Common Command Codes. CCC provides standardized commands that allow the Controller to communicate with all applicable Targets or with a specific Target.

The third category is HDR, or High Data Rate.

HDR is not simply SDR at a higher clock frequency. It uses different protocol and signaling mechanisms to achieve higher data rates per equivalent clock cycle.

I3C also supports Legacy I²C messages, which is important because one of the goals of I3C is to allow migration from existing I²C systems without requiring every device on the bus to be replaced.

And finally, I3C supports Target-initiated requests.

For example, a Target can generate an In-Band Interrupt, allowing it to request the Controller’s attention using the same bus.

The specification then introduces the concept of an I3C Frame.

At a high level, a Frame looks like:

START, Header, Data, and STOP.

The Header is particularly important because it isn’t just used for addressing. It also provides the mechanism for bus arbitration and can be involved in things such as IBI, Hot-Join, and Secondary Controller functionality.

Another important architectural rule is that only one Controller controls the bus at a time.

There may be multiple Devices that are capable of being Controllers, but only one of them can be the Active Controller at a particular time.

That brings us to Section 4.2: Controller and Target Devices.

An I3C Device can be designed as a Controller only, a Target only, or it can have both Controller and Target capabilities.

But if a Device supports both capabilities, it doesn’t operate as both simultaneously. It operates in one role at a given time.

For example, suppose we have two Controller-capable Devices.

Initially:

Device A is the Controller.

Device B is operating as a Target.

If the Controller role is transferred, the roles can change so that Device B becomes the Controller and Device A becomes a Target.

This distinction between a Device’s capabilities and its current role is very important.

So the overall picture from Section 4 is:

I3C is a two-wire bus.

That bus supports multiple communication formats.

SDR provides the fundamental communication mechanism.

CCC provides standardized management commands.

HDR provides higher-performance communication.

Legacy I²C devices can coexist where supported.

Targets can also generate defined requests toward the Controller.

And although multiple Devices may be Controller-capable, only one Device controls the bus at a time.

With this architecture in mind, we are ready to move into Section 5 — I3C Protocol, where the specification starts defining exactly how these operations happen on SDA and SCL.

And the most important place to start there is Section 5.1 — SDR Mode, because the specification itself identifies SDR as the default mode of the I3C Bus.
