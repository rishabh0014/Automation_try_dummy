5.1 Single Data Rate (SDR) Mode

Single Data Rate (SDR) is the default and fundamental communication mode of an I3C Bus.

The I3C Bus is initialized and configured in SDR Mode. SDR Mode is also used for entering other I3C modes and for several fundamental I3C features, including:

* Common Command Codes (CCC)
* In-Band Interrupts (IBI)
* Dynamic Address Assignment
* Transition from I²C operation to I3C operation

The I3C SDR protocol is significantly similar to the I²C protocol. This similarity allows I3C Devices and compatible Legacy I²C Target Devices to coexist on the same physical bus.

However, SDR introduces several important differences from I²C, particularly in signaling, data-word handling, addressing, arbitration, and I3C-specific bus-management mechanisms.

5.1.1 SDR as the Default I3C Mode

SDR is the default operating mode of an I3C Bus.

An I3C Bus does not begin directly in HDR Mode. Instead, the bus is initialized and configured using SDR.

HDR operation is entered from SDR using the appropriate Enter HDR Common Command Code.

Therefore, SDR acts as the foundation for the overall I3C protocol.

Bus Initialization
        |
        v
      SDR Mode
        |
        +------------------+
        |                  |
        v                  v
   Normal SDR          Enter HDR CCC
                           |
                           v
                       HDR Mode

5.1.2 SDR and Legacy I²C Coexistence

I3C SDR intentionally maintains substantial similarity with I²C.

This allows an I3C Controller to communicate with compatible Legacy I²C Target Devices on the same bus.

At the same time:

* I3C Targets can distinguish I3C traffic from applicable Legacy I²C traffic.
* Legacy I²C Targets should not interfere with normal I3C communication.
* Legacy I²C Controller Devices are not supported as Controllers on an I3C Bus.

This coexistence allows systems to migrate from I²C to I3C without replacing every device simultaneously.

5.1.3 Important Differences from I²C

Although SDR is I²C-like, it is not identical to I²C.

Important differences include:

Addressing

I3C supports Dynamic Address Assignment and uses I3C-specific address-management mechanisms.

Signaling

I3C uses both Open-Drain and Push-Pull signaling depending on the portion of the transfer.

Data Words

I3C SDR Data Words are 9 bits long, similar in length to I²C Data Words, but the meaning of the ninth bit differs.

For Controller-written SDR data, the ninth bit is used as Parity, rather than the Target ACK used in an I²C data byte.

Bus Management

I3C adds mechanisms such as:

* Dynamic Address Assignment
* In-Band Interrupt
* Hot-Join
* Common Command Codes
* Multiple Controller support

These mechanisms are not part of traditional I²C operation.

5.1.4 SDR Transfer Concept

At a simplified level, an SDR transfer can be represented as:

START
   |
   v
Address Header
   |
   v
ACK
   |
   v
Data Words
   |
   v
STOP

However, the detailed I3C SDR protocol differs from I²C and must be understood using the specific I3C signaling rules defined later in Section 5.1.

In particular, the Address Header and Data Word behavior have I3C-specific rules.

5.1.5 SDR Data Word

An I3C SDR Data Word consists of:

* 8 data bits
* 1 additional bit

The ninth bit has different meanings depending on the transaction.

For example, for Controller-written SDR data, the ninth bit is the parity bit associated with the preceding eight data bits.

This is different from I²C, where the ninth clock is normally used for ACK/NACK.

I3C SDR Data Word
+--------+-----+
| D7...D0|  P  |
+--------+-----+
  8 bits   1 bit

5.1.6 SDR Communication Speed

The I3C Basic v1.1.1 specification defines SDR operation with SCL clock speeds up to 12.5 MHz, subject to the applicable electrical and timing requirements.

The higher effective performance compared with traditional I²C is not achieved only by increasing the clock frequency.

I3C also improves bus efficiency through:

* Push-Pull signaling
* Reduced protocol overhead in selected operations
* Efficient data transfer
* Dynamic addressing and bus-management mechanisms

Summary

SDR is the foundation of I3C communication.

It provides an I²C-like communication mechanism while introducing I3C-specific improvements in addressing, signaling, bus management, and data transfer.

Understanding SDR is essential before studying:

* Dynamic Address Assignment

Understanding

The most important sentence from the specification is:

“SDR Mode is the default Mode of the I3C Bus.” 

This is much more important than simply remembering that SDR means Single Data Rate.

Think of the I3C protocol as having a base mode and optional advanced modes.

                 I3C
                  |
                 SDR
                  |
        +---------+---------+
        |                   |
   Normal operation      Enter HDR
                            |
                           HDR

The bus starts with SDR. You don’t power up an I3C bus and immediately start sending HDR traffic.

Why?

Because the bus first needs to establish things such as which devices exist, their addresses, their capabilities, and the bus configuration. SDR provides the common protocol foundation used for this.

The specification explicitly states that SDR is used not only for normal communication but also for CCCs, IBI, and the transition from I²C to I3C through Dynamic Address Assignment. 

Why is SDR so similar to I²C?

This is deliberate.

I3C was designed so that an existing system doesn’t necessarily need to replace every I²C device.

Imagine this bus:

             I3C BUS
          SDA + SCL
              |
       +------+------+
       |      |      |
      I3C    I3C    I²C
   Target A Target B Target

The Controller should be able to communicate with both types of devices.

Therefore, SDR deliberately retains substantial I²C-like behavior.

The specification even states that I3C traffic to an I²C Target is designed so that the Legacy I²C Target does not incorrectly respond to I3C traffic. 

But this leads to a very important point:

SDR is similar to I²C, but SDR is not I²C.

This is where you should be careful when explaining I3C to firmware engineers.

For example, if you see:

I²C:

8 data bits + ACK/NACK

you should not automatically assume:

I3C SDR:

8 data bits + ACK/NACK

The specification specifically points out that I3C SDR Data Words are also 9 bits, but the ninth bit has different semantics. For Controller-written data, the ninth bit is Parity, rather than the Target ACK used by I²C. 

That is a very important protocol-level difference.

So:

I²C Data Byte

D7 D6 D5 D4 D3 D2 D1 D0 | ACK/NACK
        8 bits            | 9th bit

whereas for the relevant I3C SDR Controller-written data:

I3C SDR Data Word

D7 D6 D5 D4 D3 D2 D1 D0 | P
        8 bits            | Parity

This is one of the reasons we shouldn’t describe I3C as simply “faster I²C.”

⸻

Why does I3C use Push-Pull in SDR?

This connects directly to what we discussed earlier.

Traditional I²C relies heavily on open-drain signaling.

The problem is that when the line needs to transition from LOW → HIGH, the device releases the line and the pull-up resistor has to charge the bus capacitance.

At higher speeds, that becomes a limitation.

I3C therefore uses Push-Pull signaling for appropriate portions of SDR, allowing the transmitter to actively drive HIGH as well as LOW.

That provides much faster transitions.

Conceptually:

I²C:

LOW ────────╮
            ╰────── HIGH
             ^
        resistor rise


I3C Push-Pull:

LOW ────────┐
            └────── HIGH
             ^
        active drive

But I3C cannot simply use Push-Pull for everything because multiple devices may need to participate in bus arbitration or request access to the bus.

That is why I3C has carefully defined transitions between Open-Drain and Push-Pull behavior.

We’ll see the exact rules when we reach 5.1.2 Bus Communication.

⸻

Why is 12.5 MHz significant?

The specification gives SDR an SCL clock rate of up to 12.5 MHz in I3C Basic v1.1.1. 

But don’t interpret that as:

“I3C is 12.5× faster than I²C.”

That’s not accurate.

I²C has several modes and different maximum clock frequencies, and effective throughput depends on protocol overhead, signaling, read/write direction, turnaround, ACK behavior, etc.

I3C improves effective performance through a combination of:

* higher clock rate,
* Push-Pull signaling,
* reduced overhead,
* more efficient data transfers,
* improved bus-management mechanisms.

So clock frequency ≠ effective data throughput.

This distinction becomes particularly important later when we compare SDR with HDR.

Now we are entering Section 5 of the MIPI I3C Basic specification, which is the actual I3C Protocol section.

The first protocol mode defined by the specification is SDR, or Single Data Rate.

The most important thing to remember here is that SDR is the default mode of the I3C Bus.

The I3C bus is initialized and configured in SDR mode. We don’t directly initialize the bus in HDR.

SDR is also used for several other important operations, including Common Command Codes, In-Band Interrupts, and the transition from I²C operation to I3C operation through Dynamic Address Assignment.

So SDR is essentially the foundation on which the rest of the I3C protocol is built.

Now, SDR is deliberately very similar to I²C.

Why?

Because I3C was designed to coexist with Legacy I²C Target devices.

For example, we could have an I3C Controller, several I3C Targets, and an existing I²C Target all connected to the same SDA and SCL lines.

The Controller needs to be able to communicate with all of them.

However, we should not conclude that I3C SDR is simply I²C at a higher frequency.

There are several important differences.

One of them is the signaling.

I3C uses both Open-Drain and Push-Pull signaling. Push-Pull allows the bus to transition faster than relying only on the pull-up resistor.

Another important difference is the Data Word.

An I3C SDR Data Word is 9 bits long, just like an I²C data transfer has nine clock cycles for a byte plus acknowledgment.

But the meaning of the ninth bit is not always the same.

For Controller-written SDR data, the ninth bit is used for parity, rather than being the Target ACK bit used in I²C.

This is a very important detail because it shows that although the protocol looks I²C-like at a high level, the actual signaling rules are different.

The specification defines SDR clock speeds up to 12.5 MHz in I3C Basic v1.1.1.

But we should not simply say that I3C is twelve-and-a-half times faster than I²C.

Actual throughput depends on the entire protocol, including overhead, signaling, direction changes, and the type of transaction.

The important idea is that I3C improves bus efficiency using a combination of higher clock rate, Push-Pull signaling, and more efficient protocol mechanisms.

So if I summarize SDR in one sentence:

SDR is the default and foundational I3C communication mode, designed to retain I²C-like compatibility while adding I3C-specific signaling, addressing, and bus-management features.
