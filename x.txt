3. I3C vs I²C

📘 Wiki Content — Ready to Paste

3.1 Overview

I3C (Improved Inter-Integrated Circuit) was designed to address several limitations of the traditional I²C (Inter-Integrated Circuit) protocol while retaining the advantages of a simple two-wire interface.

Both protocols use SCL (Serial Clock) and SDA (Serial Data) and allow multiple devices to share the same bus. However, I3C introduces improvements in areas such as speed, power efficiency, addressing, interrupt handling, bus management, and device discovery.

3.2 Physical Signaling

I²C

I²C primarily uses open-drain/open-collector signaling.

A pull-up resistor is required to bring SDA and SCL to logic HIGH.

             VCC
              |
           Pull-up
              |
              +──────── SDA
              |
          Device
              |
             GND

A device actively drives the line LOW but releases the line to allow the pull-up to bring it HIGH.

I3C

I3C uses a combination of open-drain and push-pull signaling depending on the phase and type of communication.

Push-pull signaling allows the device to actively drive both HIGH and LOW states.

       Push-Pull Driver
              |
              +──────── SDA

Why?

With open-drain signaling, the rising edge depends on the pull-up resistor and bus capacitance:

VCC ────────
          /
        /
      /
_____/ 

This limits how quickly the signal can transition from LOW to HIGH.

With push-pull signaling, the device actively drives the line HIGH, allowing a much faster transition.

Therefore:

I3C uses push-pull signaling to enable higher-speed communication and reduce the power/performance limitations associated with resistive pull-ups.

3.3 Speed

Traditional I²C provides several speed modes:

* Standard-mode — 100 kbit/s
* Fast-mode — 400 kbit/s
* Fast-mode Plus — 1 Mbit/s
* High-speed mode — up to 3.4 Mbit/s

I3C provides significantly higher data rates using modes such as:

* SDR (Single Data Rate)
* HDR (High Data Rate) modes

The exact achievable rate depends on the I3C mode and system implementation.

Why does I3C need higher speed?

Modern systems can contain many devices:

Controller
    |
    ├── Sensor 1
    ├── Sensor 2
    ├── Sensor 3
    ├── PMIC
    ├── Camera
    └── Other peripherals

All devices share the same bus.

More devices → more transactions → more bus utilization.

Therefore:

Higher bus speed allows more data to be transferred in the same amount of time and reduces the time the bus remains occupied.

⸻

3.4 Addressing

I²C

I²C devices generally use predefined addresses.

For example:

Sensor A → 0x48
Sensor B → 0x50
Sensor C → 0x68

If two devices have the same address, they can conflict unless hardware or device configuration provides a way to change one of the addresses.

I3C

I3C introduces Dynamic Address Assignment.

During bus initialization, the controller can discover devices and assign dynamic addresses.

             Controller
                  |
              Discovery
                  |
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    Target A   Target B   Target C
       |          |          |
       ↓          ↓          ↓
     0x20       0x21       0x22

Why?

This allows the controller to automatically configure the bus rather than relying entirely on hardware-defined addresses.

It also provides a standardized mechanism for discovering devices and assigning addresses.

The primary mechanism used for this is:

ENTDAA — Enter Dynamic Address Assignment

We’ll cover this in detail later.

⸻

3.5 Interrupt Handling

This is one of the biggest practical differences.

I²C

I²C itself does not provide a general in-band interrupt mechanism equivalent to I3C IBI.

A typical system may therefore use a separate GPIO:

Sensor
   |
   | INT
   ↓
GPIO
   |
   ↓
CPU

With multiple devices:

Sensor 1 ── INT1 ──┐
Sensor 2 ── INT2 ──┤
Sensor 3 ── INT3 ──┤── CPU
Sensor 4 ── INT4 ──┘

This consumes GPIO pins.

I3C

I3C introduces IBI — In-Band Interrupt.

Sensor
   |
   | IBI
   ↓
I3C Bus
   |
   ↓
Controller

The target uses the I3C bus to request the controller’s attention.

Why?

Modern systems may have many peripheral devices.

Dedicated interrupt GPIOs for every device increase:

* Pin count
* Board routing
* Hardware complexity
* Software interrupt management complexity

IBI allows the interrupt request to travel through the existing I3C bus.

In-band means that the notification is transmitted using the communication bus itself rather than requiring a separate physical interrupt line.

⸻

3.6 Device Discovery

I²C

I²C doesn’t provide a standardized mechanism equivalent to I3C’s dynamic device discovery process.

The system generally knows which devices are expected and what addresses they use.

For example:

Firmware configuration:

0x48 → Temperature Sensor
0x50 → EEPROM
0x68 → RTC

I3C

I3C provides standardized mechanisms to identify and configure devices.

The controller can obtain information such as:

* PID — Provisional ID
* BCR — Bus Characteristics Register
* DCR — Device Characteristics Register

and assign dynamic addresses.

Why?

This enables more automatic bus initialization and device management.

Instead of the firmware having to rely entirely on a fixed list of addresses, the controller can discover devices and obtain their characteristics.

⸻

3.7 Common Command Codes — CCC

I²C

I²C defines the basic communication mechanism, but device-specific configuration commands are generally defined by individual device specifications.

For example:


I²C Controller
      |
      | Device-specific command
      ↓
   Sensor

Different devices may have completely different command structures.

I3C

I3C defines Common Command Codes (CCC).

             Controller
                  |
            Standard CCC
                  |
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    Target A   Target B   Target C

CCC provides standardized commands for common operations such as:

* Device discovery
* Address assignment
* Reading device information
* Bus management
* Enabling/disabling features

Why?

Without CCC, every vendor could implement different mechanisms for common bus-management operations.

CCC provides a standardized control mechanism that an I3C controller can use across compliant devices.

⸻

3.8 Hot-Join

I²C

I²C does not define an equivalent standardized Hot-Join mechanism.

I3C

I3C supports Hot-Join.

A target that becomes available after the bus has been initialized can request to join the active bus.

Bus already running
       |
       |
   New Target
       |
   Hot-Join
       |
       ↓
   Controller
       |
       ↓
Dynamic Address Assignment

Why?

Modern systems may have devices that become available dynamically.

Hot-Join allows these devices to notify the controller without requiring a complete system restart or bus reinitialization.

⸻

3.9 Multi-Controller Support

I²C traditionally revolves around a master-controlled bus, although modern I²C does define multi-master operation.

I3C provides a more structured controller model, including:

* Primary Controller
* Secondary Controller
* Controller handoff

Why?

Some systems may contain multiple devices capable of controlling the bus.

I3C provides mechanisms to manage these roles and transfer control of the bus when required.

For a basic I3C implementation, however, you’ll most commonly encounter a single Primary Controller with multiple Targets.

⸻

3.10 I²C Coexistence

One of I3C’s important design goals is compatibility with existing I²C devices.

An I3C bus can contain:

                I3C Controller
                      |
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
   I3C Target     I3C Target     Legacy I²C
                                  Target

This allows systems to introduce I3C devices without necessarily replacing every existing I²C peripheral.

Why?

I²C has an enormous installed base.

If I3C required every existing device to be replaced, adoption would be much more difficult.

Therefore, I3C was designed to support coexistence with supported legacy I²C devices.

⸻

3.11 Power Consumption

I²C’s open-drain signaling uses pull-up resistors.

When a device holds the line LOW:

VCC
 |
 R
 |
 +──── Device ─── GND

Current flows through the pull-up resistor.

I3C’s push-pull signaling reduces the need for this type of continuous resistive pull-up current during normal high-speed communication.

Why?

Modern mobile and embedded systems are highly power-sensitive.

Reducing unnecessary bus power consumption becomes increasingly important as the number of devices and amount of communication increases.

🧠 The Most Important Point

Don’t memorize the table.

Understand the chain of problems → solutions:

              I²C Limitations
                    |
      ┌─────────────┼──────────────┐
      ↓             ↓              ↓
    Speed       GPIO Interrupt   Addressing
      ↓             ↓              ↓
   I3C SDR/HDR      IBI       Dynamic Address
      |
      |
      └──────────────┐
                     ↓
              Better 2-wire bus
                     |
        ┌────────────┼────────────┐
        ↓            ↓            ↓
       CCC        Hot-Join    I²C coexistence

So when someone asks you “Why does I3C have IBI?”, don’t answer:

“Because I3C specification defines IBI.”

Instead:

“Because using a dedicated GPIO interrupt for every peripheral doesn’t scale well. I3C therefore allows targets to notify the controller over the same two-wire bus.”

That’s the kind of explanation that shows you understand the protocol rather than just memorizing its features.

🎤 Speech for This Section

You can present it roughly like this:

“Now let’s compare I3C with I²C and, more importantly, understand why these differences exist.”

“At the physical level, both I²C and I3C use the same basic two signals: SDA and SCL. So I3C keeps the advantage of a simple two-wire interface.”

“The first major difference is signaling. Traditional I²C primarily relies on open-drain signaling, where the pull-up resistor is responsible for bringing the signal HIGH. This limits how quickly the signal can rise because of the resistor and bus capacitance.”

“I3C introduces push-pull signaling for its high-speed communication. The device can actively drive the signal HIGH as well as LOW, allowing faster transitions and better power efficiency.”

“The second major difference is speed. Modern systems can have many sensors and peripheral devices sharing the same bus. As the amount of communication increases, the bus can become a bottleneck. I3C therefore provides higher-speed SDR and HDR modes.”

“The next difference is addressing. I²C generally relies on predefined device addresses. I3C introduces dynamic address assignment, where the controller can discover devices and assign addresses during bus initialization.”

“Another very important feature is interrupt handling. In an I²C-based system, a sensor commonly needs a separate GPIO to tell the processor that it has new data. If we have many sensors, we need many interrupt lines. I3C solves this with In-Band Interrupts, or IBI, where the target uses the I3C bus itself to request the controller’s attention.”

“I3C also introduces Common Command Codes, or CCC, which provide standardized commands for operations such as device discovery, address assignment, and bus management.”

“Then we have Hot-Join, which allows a device to request joining an already-running I3C bus.”

“And finally, one of the most important adoption advantages is that I3C can coexist with supported legacy I²C devices. So I3C doesn’t require an entire system to replace all its existing I²C peripherals at once.”

“So the key takeaway is that I3C is not simply ‘faster I²C’. It retains the simple two-wire architecture but adds mechanisms for higher performance, better power efficiency, dynamic device management, interrupt handling, and easier integration of modern peripherals.”

⚠️ One nuance to be careful about in your Wiki

I’d avoid saying simply “I²C has a maximum speed of 400 kHz”. That’s a common oversimplification. I²C has multiple defined speed modes, including Fast-mode Plus and High-speed mode.

Similarly, don’t say “I3C always runs at X MHz.” I3C has different operating modes and the actual rate depends on the mode and implementation.

We’ll get into the actual SDR/HDR speeds and signaling when we reach the transfer section. That will also make the physical-layer explanation much clearer.
